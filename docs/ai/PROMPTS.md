## Phase 5: Plan review (revision 2)

Prompt, in short: act as a staff engineer reviewing the submission; update `PLAN.md` and its docs for effective-dated salaries, country/currency separation, import idempotency, fairness wording, audit logs, security, an "Ask Paywise" query feature, P0/P1/P2 priorities and testing, without writing application code or redesigning the stack.

How it was done: the AI read the whole plan, every doc and the code the brief touched before editing, then listed contradictions between the plan, the docs and the code (e.g. "effective date ≤ today" vs. scheduling; "currency derived from country" vs. overrides; "raise cost read-only" vs. the built apply step; legal "EU 5% trigger" wording; "no per-user audit"). Docs mark every revision-2 item as **planned**, so they don't claim unbuilt features.

Decisions taken (and alternatives rejected): keep a cached current salary and promote due revisions daily, on cold start and on write (rejected: deriving the current salary in every query, which touches every measured query); same-date changes as linked corrections (rejected: editing revisions); Postgres for idempotency keys and login counters (rejected: Redis); audit written by services in the same transaction (rejected: database triggers, which can't see the actor); Ask Paywise as a rule-based parser to a validated plan (rejected: LLM-generated SQL).

Review findings recorded as work rather than hidden: bulk-raise row locks taken in no fixed order (deadlock risk), hard-coded fairness thresholds, a stale test count in the README, frontend component tests promised but not written, and a deployment never exercised.

## Phase 6: Schema review

Prompt, in short: act as a senior backend engineer (PostgreSQL, financial data) and review the schema for employee/compensation separation, effective dates, overlap, concurrent salary updates and isolation, currency, audit vs history, import provenance and idempotency, constraints, indexes and 10k-row aggregation. Deliver an ER diagram, a schema, transaction boundaries, queries, edge cases and tests.

Output: [`docs/SCHEMA_REVIEW.md`](../SCHEMA_REVIEW.md), a proposal that builds on PLAN.md revision 2. Each claim was checked by running it: 24 constraint checks on PGlite, and four concurrency races on local Postgres 17 in a scratch database. New findings: a lost-decision race (fixed with a `basedOnRevisionId` check, returning 409), a race in the planned promotion job that can overwrite a correction in the cache (fixed by locking first, then updating in a new statement), the deadlock reproduced, and a composite FK that pins the cached salary to a real revision.

## Phase 7: Match our other projects (domainstack)

Prompt, in short: compare Paywise with our domainstack backend and frontend, then make Paywise match them: Express instead of Hono, `http-errors`, the same structure and client, keeping the tests. Decisions asked of the user: keep the shared Zod validation (not express-validator), move the web app to domainstack's layout and client but keep TanStack Query, Jotai and react-hook-form inside it, and switch to JWT Bearer auth with the token in `localStorage`.

Output: Express routes with per-route `verifyAccessToken` + Zod validator middleware, `asyncHandler` controllers, `http-errors` with a stable `code`, a central error handler; the web app under `src/` with `lib/api-client.ts`, `lib/auth-client.ts`, `context/AuthContext.tsx`, `components/<feature>/` and `hooks/useX.ts`. Route tests kept their shape through a loopback test server. Checked in headless Chrome: redirect to sign in, wrong password, sign-in, every page, CSV export, sign-out.

Follow-up: the web app moved to our referral-stack frontend's layout (no `src/`; `app/(Auth|Main)`, `components/{block,shared,layout}`, `utils/{apis,services,constants,forms,helpers}`, `@types`). Decisions asked of the user: axios in `utils/services` with TanStack Query kept in `utils/apis`, the token in a js-cookie with a server-side redirect in `proxy.ts` (replacing the client-side gate), and `@types` for web-only types while API shapes stay in `@paywise/shared`.

## Practices that kept AI output honest

- **Rules in `CLAUDE.md`**: money only through `money.ts`, validation only in shared Zod schemas, salary changes only through the revision service, SQL aggregates only.
- **Small hand-computed fixtures**, so a wrong formula fails loudly instead of matching a wrong expectation.
- **Exercising features on realistic data** (the 10k seed) and **looking at the UI** (screenshots), not only unit tests. Two of the most important fixes above came from this.
- **A verification gate** before every commit, and fixing the gate when it turned out to leak.

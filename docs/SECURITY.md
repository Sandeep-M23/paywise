# Security

Paywise holds salary data for 10,000 people, so the bar is "safe for a public demo URL with one HR user", not enterprise IAM. Everything in the table below is built.

## Threat model (what we defend against)

| Threat                                     | Defence                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Anonymous access to salaries               | Every API route requires a valid access token (`Authorization: Bearer`) except `/health` and `/auth/login`; `proxy.ts` sends signed-out visitors to `/login` before any page renders                                                                                                                                                                |
| Stolen or guessed password                 | scrypt (random salt) hash in env; constant-time compare; the hash runs even for an unknown email (no timing oracle); the error never says which part was wrong                                                                                                                                                                                      |
| Token forgery or reuse                     | JWT signed with `JWT_ACCESS_SECRET` (HS256 pinned on sign and verify, so `alg: none` is refused); 8-hour expiry; checked on every request; forged, foreign and expired tokens are tested                                                                                                                                                            |
| Token theft via script (XSS)               | Accepted trade-off (see below): the token is in a cookie readable by script. React escapes output, there is no `dangerouslySetInnerHTML` on user data, the web pages' CSP only lets scripts send requests to their own origin (`connect-src 'self'`), and the 8-hour expiry limits the window                                                       |
| Cross-site request forgery                 | Not possible by design: the browser never sends the Bearer token on its own, so a forged cross-site request arrives unauthenticated                                                                                                                                                                                                                 |
| Database traffic interception              | TLS to hosted Postgres with the server certificate verified (`rejectUnauthorized: true`); hosts with a private CA supply it through `NODE_EXTRA_CA_CERTS`                                                                                                                                                                                           |
| Other sites calling the API from a browser | CORS is off unless `CORS_ORIGIN` lists an origin; the web app needs none, since the browser only talks to the web domain, which proxies `/api`                                                                                                                                                                                                      |
| Known-vulnerable dependencies              | `npm audit` is clean; two transitive packages are pinned to fixed versions through `overrides` in the root `package.json` (`uuid` under Sequelize, `minimatch` under the shadcn CLI)                                                                                                                                                                |
| SQL injection                              | Sequelize named replacements, never string-built SQL; whitelisted sort columns                                                                                                                                                                                                                                                                      |
| CSV formula injection in exports           | Cells starting with `=`, `+`, `-`, `@`, tab or CR are prefixed with `'` (OWASP)                                                                                                                                                                                                                                                                     |
| Oversized uploads                          | 4.4 MB body limit for imports, 1 MB elsewhere, and 10,000 rows → 413                                                                                                                                                                                                                                                                                |
| Salary data in logs                        | Request bodies, tokens and salary values are never logged: `morgan` logs method, path, status and time (locally only); unexpected errors are logged by name, message and stack                                                                                                                                                                      |
| Error details leaking                      | Only 4xx errors carry a message; anything else is a generic `500 internal`, and the web app shows its own text for 5xx                                                                                                                                                                                                                              |
| Clickjacking, MIME sniffing                | `helmet` on every API response; the web pages send their own CSP (`frame-ancestors 'none'`, `object-src 'none'`), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy` and `Permissions-Policy` (`next.config.ts`)                                                                                                                                 |
| Silent history changes                     | Salary changes are added, never edited or deleted: mistakes become correction entries and scheduled changes are cancelled, not removed (the one edit is moving the hire revision when the hire date is corrected). Foreign keys are `ON DELETE RESTRICT`, so history can't be deleted with an employee or import. Each revision records who made it |
| Re-identifying people through statistics   | Gender comparisons are hidden when either group has fewer than 5 people; gender is never listed or exported                                                                                                                                                                                                                                         |

## Assumptions and limitations

- **One shared HR account.** Changes are recorded as "hr@acme.test", not a person. Multiple users, roles, SSO and per-person accountability are v2.
- **Stateless tokens.** There is no server-side session store, so a token can't be revoked before it expires; signing out only removes it from the browser. Rotating `JWT_ACCESS_SECRET` signs everyone out.
- **Token in a script-readable cookie, not an `HttpOnly` one.** Chosen to match our other apps (referral-stack): the cookie lets `proxy.ts` redirect on the server, and the API only ever reads the `Authorization: Bearer` header, never the cookie, so there is no CSRF surface. The cost is that an XSS bug could read the token; an `HttpOnly` cookie would hide it from script but the API would then have to accept cookies, bringing CSRF back.
- **Data:** every environment, including the deployed demo, uses the synthetic seed. Reviewer credentials are shared out of band, never committed.
- **Secrets:** `HR_PASSWORD_HASH`, `JWT_ACCESS_SECRET` and the database settings (`DATABASE_URL`, or `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`, `DB_SSL`) live in environment variables; `.env` files are git-ignored.

## Not covered (next steps)

- **Login rate limiting.** One account on a private demo; the hosting platform's firewall handles brute force. Next to add if more people get access.
- **A separate audit log** of every edit (beyond salary history and the import log), append-only at the database level.
- **Import replay protection.** The button is disabled while an import runs; a server-side idempotency key would make retries safe.
- **A least-privilege database role.** The API connects as the database owner Neon creates, which can also change the schema. A role limited to reading and writing rows would contain the damage of a bug; the schema would then be applied with the owner role only.
- **A strict, nonce-based CSP.** Next.js needs inline scripts, so `script-src` allows `'unsafe-inline'`; nonces would remove that but make every page render per request.
- **Encryption** beyond the Postgres host's defaults, field-level encryption of salaries, and data retention and erasure (GDPR) flows.
